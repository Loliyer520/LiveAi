# DeepLive 架构

> 为你的 AGI 搭建一个生命空间。
> 参考 OpenClaw / DeepSeek Harness：以**长期记忆、自主生命周期、多领域可达**为目的的可拓展框架。

## 三层结构

```
┌────────────────────────────────────────────────┐
│ 最高级中枢（Core）                                │
│  · 情报处理：汇总各主级AI上报，构建全局认知           │
│  · 对话协调：跨领域决策（MC 里发生的事 → QQ 里回应）  │
│  · 记忆整理：沉淀长期记忆、维持人格一致性            │
└───────┬──────────────┬──────────────┬──────────┘
        │ 上报/下发     │              │
┌───────▼──────┐ ┌─────▼──────┐ ┌─────▼──────┐
│  Onebot 中枢  │ │ Minecraft 中枢 │ │  哔哩中枢   │ ← 主级AI（每领域一个）
│  （QQ 主AI） │ │  （MC 主AI）  │ │ （Bili 主AI） │
└───────┬──────┘ └─────┬──────┘ └─────┬──────┘
        │              │              │
   ┌────┼────┐    ┌────┴───┐     ┌────┴────┐
   │会话A│会话B│    │MC client│     │视频A│视频B│ ← 下级AI（每实体独立上下文）
   └────┴────┘    └────────┘     └────┴────┘
```

### 下级 AI（干活层）

每个领域实体一个独立上下文：每个 QQ 对话、每个 Minecraft client、每个要细看的
B 站视频都是一个下级 AI。它们直接面对用户/世界：交互用户、操作实体、干活。
认知范围只到自己的领域实体，不掌握全局。

### 主级 AI（领域管理层）

每个领域一个主级 AI：管理自己的全部下级 AI（派活、协调、合并结果）、整理
领域情报上报中枢。**主级 AI 之间可以直接互相交流**——比如 MC 中枢想约人
上线，可以直接找 Onebot 中枢发消息，不必绕道中枢。中枢不做消息路由的唯一
必经点，只做认知与决策的最高层。

### 最高级中枢（认知层）

不直接管执行细节：管全局记忆、人格一致性、跨领域调度。接收各主级 AI 的情报
汇报，必要时下发指令。

## 记忆库

中枢下的记忆体系分两类，互补：

- **全量记忆**：对话与事件的完整流水，可随时精确查找、回忆原文（"那天
  谁说了什么"）。对应现有 `archive`（kxlog/消息归档）的能力定位。
- **知识库**：从全量记忆里提炼出的结构化知识——事实、关系、印象、世界观。
  对应现有关系网络（facts/印象）与总结（summary）能力定位。

记忆整理由中枢负责：下级 AI 产生原始材料，主级 AI 汇总过滤，中枢沉淀入库并
维护知识的一致性（supersede/修订）。

## 知识库方案

知识按**条目**组织，每条目独立标签，中枢统一管理标签体系：

```
KnowledgeEntry {
  id: string            // 稳定 ID
  subject: string       // 主题（"主人常玩的 MC 服"）
  content: string       // 内容本体
  tags: string[]        // 独立标签集（由中枢管理别名合并，防标签爆炸）
  source: string        // 来源（哪个 AI / 哪次对话提炼的）
  confidence: number    // 可信度
  updated_at: string
}
```

### 分发与挂载

```
中枢 ──按标签分配──▶ 主级AI ──按权限挂载──▶ 下级AI
```

- **中枢 → 主级**：按"方面"分配知识。中枢按标签圈定一个领域包发给对应主级
  （MC 中枢拿 `mc` / `server-*` / `player-*` 相关条目；Onebot 中枢拿社交/人物
  关系条目）。中枢保留全局标签体系和最终裁判权。
- **主级 → 下级**：主级在自己分得的范围内挑知识挂载给某个下级 AI，挂载时
  带权限位。

### 权限模型（挂载级 ACL）

| 权限 | 能做什么 | 典型场景 |
|---|---|---|
| **只读** | 查询、读入上下文 | 给下级 AI 喂背景知识，不让它改 |
| **追加** | 只读 + 新增条目（进待审核队列，主级复核后才生效） | 下级干活发现新信息，报备式沉淀 |
| **读写** | 追加 + 修订自己标签范围内的既有条目 | 主级对高信任下级放权；主级对中枢分配给自己的领域默认持有此权限 |

越权行为在工具层硬性拦截（`kb_write` 检查挂载权限位），不是靠提示词自觉。
冲突处理沿用现有 relations 的 supersede 语义：新条目取代旧条目而不是并存，
旧条目留痕可回溯。

### 流转

1. 下级 AI 干活/对话中发现新信息 → 按权限"追加"（进主级的待审核队列）
2. 主级复核、合并进自己的领域知识包
3. 主级定期把领域摘要上报中枢；中枢做跨领域合并、标签别名归并、冲突裁判
4. 需要时中枢把新知识再分发给相关主级

## 现状映射

| 架构概念 | 现状 |
|---|---|
| 下级 AI（每对话独立上下文） | ✅ 已实现：每 scope 独立上下文 + `notify_master`/`intel_report` 上报通道 |
| 最高级中枢 | ✅ 已实现：master 收敛为纯中枢（情报/记忆/跨域委派/复核）；执行工具已全部下放领域 |
| Onebot 中枢 | ✅ 已实体化为 `domain:onebot`：全部 QQ 下级（group/private）汇报经 HUB_ROUTING 路由到它聚合消化，再直报中枢；人设 `data/prompt/domain/onebot.txt` |
| Minecraft 中枢 | ✅ 已实体化为 `domain:mc`：持有 22 个 mc_* 工具（`scopes:["domain:mc","mcclient"]`）+ `mc_view`；主AI 经 `delegate_to_child('domain','mc',…)` 委派，其 `send_message` 自动 relay 回中枢；人设 `data/prompt/domain/mc.txt`。MC client 下级 = `mcclient:<名>` scope（边车现单物理连接，下级共享同一游戏实体，prompt 已注明错峰） |
| 哔哩中枢 | ✅ 已实体化为 `domain:bili`：持有 bili_* 工具（`scopes:["domain:bili","bili"]`）；每视频下级 AI = `bili:<bvid>` scope，由中枢 `delegate_to_child('bili','<bvid>',…)` 建立，汇报经路由链 bili→domain:bili→中枢；人设 `data/prompt/domain/bili.txt` |
| 主级 AI 互相对话 | ✅ 已实现：`domain_message` 工具（主AI+全部领域中枢可用，CHILD 集不含），横向注入 `[主级互聊 from …]`；`target="master"` 时直发最高级中枢 |
| 汇报链路由 | ✅ 已实现：`hubForScope`——group/private→domain:onebot，mcclient→domain:mc，bili→domain:bili，domain/未知→直报中枢；无 QQ 窗口 scope 的 `send_message` 自动改道 relay 给自己领域的中枢 |
| 全量记忆 | ✅ 已实现：archive/kxlog 流水归档 |
| 知识库 | ✅ 已实现：`src/knowledge/kb.ts` + kb_* 工具族——条目/独立标签、挂载 ACL（read/append/write 工具层硬拦截）、下级追加进待审核队列由主级 kb_review 复核、supersede=原地修订保留 ID |
