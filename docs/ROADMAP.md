# DeepLive 发展计划书

> 对标 OpenClaw：不是做单渠道聊天机器人，而是做**多环境、可拓展的智能体框架**。
> 本文档是方向性规划，随实现滚动修订。最近更新：2026-10-26。

## 一、定位

**OpenClaw 是什么**：个人 AI 助手网关——多渠道接入（IM/邮件/日历）、技能插
件、长期记忆、本地优先。它的形态是「一个助手，很多触角」。

**DeepLive 的差异化**：不是一个助手伸出触角，而是**一个智能体社会**——
三层架构（中枢 → 领域主级 AI → 下级 AI）已经在代码里落地，每个领域实体
（QQ 会话、MC 客户端、B 站视频）都是有独立上下文、记忆和人设的个体。这是
OpenClaw 没有的结构：它管「接入」，我们管「生态」。

一句话：**OpenClaw 让 AI 无处不在，DeepLive 让 AI 各有所居。**

## 二、现状盘点（2026-10）

已实现，且经过真机验证：

| 层 | 能力 | 状态 |
|---|---|---|
| 接入 | QQ（NapCat 正/反向 WS）、面板内对话 | ✅ |
| 领域 | Onebot / Minecraft / 哔哩哔哩 三个中枢 + 下级 scope | ✅ |
| 插件 | 声明式 HTTP manifest（免代码加工具）、SSRF 防护、密钥托管、热加载 | ✅ |
| 记忆 | 全量流水 archive + 结构化知识库（条目/挂载/审核）+ 关系网 + 后台总结 | ✅ |
| 自主 | 定时任务调度器、主动发消息巡检、总开关热切换 | ✅ |
| 运维 | Web 面板（10+ 页面/抽屉导航/新手向导）、检查更新、244 项测试 | ✅ |
| 部署 | systemd 三单元（主 bot / 小说 bot / MC 边车） | ✅ |

真实规模：约 1.7 万行 TS，4 个插件 25+ 工具，5 个面板插件子页面。

## 三、与 OpenClaw 的差距

诚实评估，按影响排序：

1. **渠道广度**：OpenClaw 十几种接入；我们只有 QQ + 面板。
2. **插件生态**：OpenClaw 有社区技能市场；我们的 manifest 规范刚成型，
   无版本管理、无依赖声明、无第三方作者。
3. **安装门槛**：OpenClaw 一行命令起步；我们要求 systemd + Node + NapCat
   手工配置（新手向导只解决了面板侧）。
4. **可观测性**：OpenClaw 有结构化日志/trace；我们的卡顿/故障排查靠
   临时探针（MC3D 的 stall 探针模式证明有效，但未沉淀为框架能力）。
5. **文档**：architecture.md 一篇 vs 对方完整文档站。

## 四、路线图

### P0 · 框架地基（进行中 → 2026 Q4）

目标：让「加一个领域」和「加一个插件」都有标准动作。

- [x] 插件子页面通用化（任意 manifest 插件自动获得面板页）
- [x] **领域注册表标准化**：`data/domains/<id>.json` 声明式注册——可覆盖
  内置领域（title/description）或零代码新增领域（child_types 自动挂
  汇报路由）；坏文件记录不崩溃（tests/roadmap-p0.test.ts）
- [x] **插件 manifest v2**：version/min_core 展示 + `config` 配置项声明
  （面板自动生成表单，值存 _config.json，请求模板 `{{config.KEY}}` 引用，
  类型强转 + 未声明 KEY 丢弃，面板/试玩同路径解析）
- [x] **统一探针框架**：`observability/probe.ts`（record/withProbe/环形
  缓冲/慢事件现场，探针永不影响业务路径）；已埋 chat.turn、plugin.call、
  plugin.try 三点；面板新增「性能」页（慢调用 TOP + 事件现场 + 清零）

### P1 · 渠道与环境扩展（2026 Q4 → 2027 Q1）

目标：验证「多环境」不是三个点，而是 N 个点。

- [ ] **WebSocket 通用渠道**：定义 DeepLive 渠道协议（消息/事件/动作
  三类帧），让任何环境写一个 adapter 就能接入——第一个验证者：
  Chaty（自有 IM，协议已熟）
- [ ] **Minecraft 中继服模式**：从「边车进别人服」扩到「bot 自己开服
  当世界宿主」（MC3D 服务器权威经验可复用）
- [ ] **番茄/内容领域**：novel 从工具插件升级为领域中枢（每本书一个
  下级 AI，和 bili 每视频一个 AI 同构）

### P2 · 生态与分发（2027 Q1 → Q2）

目标：别人能写插件、能装 DeepLive。

- [ ] **插件仓库**：GitHub 仓库 + manifest 索引 JSON，面板「插件市场」
  页一键安装（git clone 到 data/plugins/ + reload，全部已有零件）
- [ ] **插件签名与权限分级**：`allow_internal`（内网访问）等危险能力
  要求签名或主人显式确认，面板上分级展示
- [ ] **一键部署脚本**：单命令装 Node/拉仓/配 systemd/引导 NapCat，
  把现在的手工步骤压成一条线（新手向导收集的参数直接生成 config）
- [ ] **文档站**：架构、插件开发指南、渠道 adapter 指南三篇起步

### P3 · 智能深化（持续）

- [ ] **跨领域记忆检索**：中枢情报库已建，下一步让下级 AI 能查到
  「别的领域发生的相关事」（受 KB 挂载 ACL 约束）
- [ ] **SSM 结构化记忆模型**：自研记忆模型（A100 上已训练 v4）作为
  中枢的记忆整理引擎，替代部分 LLM 总结调用
- [ ] **多模态**：视觉角色已通（vision role），下一步接入领域事件
  触发截图理解（MC 视觉已验证）

## 五、工程原则（不因扩张动摇）

1. **masterQq 唯一信任根**：任何新渠道/插件不给 bot shell 类能力。
2. **声明式优先**：能写 manifest 解决的，不写代码（novel/weather 零代码
   上线已验证这条路的正确性）。
3. **测试随行**：每加一个框架能力，测试数同步涨（当前 244）。
4. **真实环境验收**：面板改动必须真机 Chromium 截图，bot 改动必须
   e2e 过真实服务——「看起来对」不算对。
5. **插件是公民**：新功能先问「能不能做成插件」，核心只留调度、记忆、
  会话、安全。

## 六、风险

| 风险 | 缓解 |
|---|---|
| 渠道 adapter 各自失控 | 渠道协议 P1 先行，adapter 只许实现协议不许发明协议 |
| 第三方插件带毒 | P2 签名分级 + SSRF 防护已在内核层 |
| 三层架构过度设计小场景 | 单领域部署必须能跑（deeplive-novel 已验证裁剪路径） |
| 维护者只有一人 | 文档与一键部署是 P2 的优先级而非锦上添花 |
